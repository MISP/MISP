# Database engines: what differs

MISP 3.0 runs on MariaDB, MySQL and PostgreSQL. This page lists where the
engines behave differently, and what changed for an instance coming from 2.5
(MariaDB or MySQL). It is a lookup, not a tutorial: for how to write a
migration read [database-migrations.md](database-migrations.md); for how to
upgrade read [UPGRADE.md](../UPGRADE.md).

| | 2.5 as shipped | 3.0 MariaDB | 3.0 MySQL | 3.0 PostgreSQL |
|---|---|---|---|---|
| Supported | MariaDB, MySQL | 10.11 or later | 8.4 or later | 16 or later |
| Install baseline | `INSTALL/MYSQL.sql` | `INSTALL/MARIADB.sql` | `INSTALL/MYSQL.sql` | `INSTALL/POSTGRESQL.sql` |
| Default `sql_mode` | per server | `STRICT_TRANS_TABLES`, `ERROR_FOR_DIVISION_BY_ZERO`, … | the same, plus `NO_ZERO_DATE`, `NO_ZERO_IN_DATE`, `ONLY_FULL_GROUP_BY` | not applicable |

Below the floor of a family, a migration that needs the target collation
defers instead of guessing.

## 1. Types and defaults

| | 2.5 | 3.0 (all engines unless stated) |
|---|---|---|
| Ids and references | `int(11)`, 41 `int(10) unsigned`, 5 `int(11) unsigned` | `bigint`, signed, everywhere (the 12 `bigint unsigned` become signed). PostgreSQL: `bigint GENERATED BY DEFAULT AS IDENTITY`, not `serial` |
| Epoch columns | 35 columns of 32-bit seconds (overflow in 2038; three unsigned, 2106) | `bigint` seconds. The API still returns them as before |
| `user_login_profiles.created_at` | `TIMESTAMP` (2038) | `DATETIME` on MariaDB and MySQL, keeping the server-zone value; PostgreSQL already had `timestamp` |
| Expression defaults | `correlation_rules.created DEFAULT unix_timestamp()`, the only one. MySQL 8.4 refuses an unparenthesised expression default, so 2.5's `MYSQL.sql` loads on 8.4 with exactly this one error | none. The column defaults to `0` and the model sets the time. A migration that declares an unknown expression default is a hard error |
| Display widths in the baseline | `int(11)` | `MARIADB.sql` keeps them (`bigint(20)`); `MYSQL.sql` has none (`bigint`) |
| `logs`, `audit_logs` | `int` ids; `logs` in `utf8mb3_bin` with no index but the key on a clean install, `audit_logs` in `utf8mb4_unicode_ci` | `bigint` ids, `logs` in `utf8mb4_bin` and `audit_logs` in the CI collation, with the indexes the log views read by. Fresh installs only: an upgraded instance keeps the 2.5 layout until `Console/cake LogTables upgrade`, and MISP works with either. On the old `logs`, 4-byte characters are stored as `U+FFFD` |
| Row format | server default | all tables `DYNAMIC`, which both MariaDB 10.11 and MySQL 8.4 have as `innodb_default_row_format`. Indexes over 767 bytes need it. The baselines do not state it: a server configured for `COMPACT` would create other tables than the migrations do |

## 2. Collations and comparison

Three classes are in use. MISP names them by token, and each engine resolves a
token to its own collation.

| Token | MariaDB | MySQL | PostgreSQL |
|---|---|---|---|
| `CI` (names, tags, values) | `utf8mb4_uca1400_ai_ci` | `utf8mb4_unicode_520_ci` | the database default (case-sensitive); case-insensitive only where a query or index says `lower()` |
| `BIN` | `utf8mb4_bin` | `utf8mb4_bin` | the database default |
| `ASCII` (uuids, hashes) | `ascii_bin` | `ascii_bin` | the database default; no per-column character set |

The baselines of MariaDB and MySQL start with an `ALTER DATABASE` that sets the
database default to the `CI` collation, so a table created without one gets it.

How the engines compare strings (measured on MariaDB 10.11.14, MySQL 8.4.11 and
PostgreSQL 16.15, `en_US.UTF-8`). `=` means the comparison is true.

| | `general_ci` (2.5) | `unicode_ci` (2.5) | MariaDB 3.0 `uca1400_ai_ci` | MySQL 3.0 `unicode_520_ci` | PostgreSQL |
|---|---|---|---|---|---|
| `'A' = 'a'` | yes | yes | yes | yes | no |
| `'e' = 'é'` | yes | yes | yes | yes | no |
| `'ß' = 'ss'` | no | yes | yes | yes | no |
| `'ß' = 's'` | yes | no | not measured | not measured | no |
| `'a' = 'a '` (trailing space) | yes | yes | yes | yes | no |
| `'😀' = '😺'` | **yes** | **yes** | no | no | no |

- **Emoji are told apart** by the 3.0 collations; 2.5's treated every 4-byte
  character as equal. `utf8mb4_bin` also tells them apart.
- **Trailing spaces** are ignored by every MariaDB and MySQL collation MISP
  uses, `utf8mb4_bin` included (`PAD SPACE`). MySQL's newer `0900` collations
  are `NO PAD`, which is why 3.0 uses `unicode_520_ci` instead: a lookup for
  `Quasar RAT` must still find a stored `Quasar RAT `. PostgreSQL never ignores
  trailing spaces. Stored bytes are never changed.
- **Case-sensitive uuids and hashes.** On MariaDB and MySQL they are `ascii_bin`
  everywhere in 3.0 (2.5 mixed `ascii_general_ci`, `utf8mb3_bin` and
  `unicode_ci`). About thirty columns that were case-insensitive are now
  case-sensitive: an upper-case uuid stops matching its lower-case form.
  PostgreSQL always was case-sensitive.
- **Literals kept as they were.** `collections.type`,
  `collection_elements.element_type` and the `*_object_type` columns of notes,
  opinions and relationships keep `ascii_general_ci` on MariaDB and MySQL
  (seven occurrences in each baseline); PostgreSQL has no equivalent.
- **Sort order** follows the collation: UCA 14 on MariaDB, UCA 5.2 on MySQL, the
  database's locale on PostgreSQL. An `ORDER BY` on strings can differ between
  engines.

**The same query, different result.** On PostgreSQL a lookup that depends on
case or trailing spaces finds nothing where MariaDB and MySQL find a row: a
`restSearch` tag filter in another case, a tag or sharing group name, a user
email, a report name with `ß`. The attribute values are the exception: a
`lower(left(value, 128))` index makes their lookup case-insensitive on
PostgreSQL too, but accents, no-break spaces and trailing spaces only fold on
MariaDB and MySQL.

## 3. Indexes

| | 2.5 | MariaDB / MySQL 3.0 | PostgreSQL 3.0 |
|---|---|---|---|
| `varchar` columns | prefixes such as `type(16)`, `object_relation(32)`, `meta-category(16)` | indexed whole | indexed whole |
| `text` columns | a prefix such as 191 | the same prefix | a single-column, non-unique prefix index becomes a **hash** index (equality only); a unique one becomes a full btree |
| One composite index with a prefix | `warninglist_entries.idx_wle_list_value (warninglist_id, value(191))` | kept | left out: a prefix on text in a composite index has no PostgreSQL form |
| Substring search on attribute values | not available | `FULLTEXT`, built with `innodb_ft_enable_stopword = 0`; matches from the start of a word | `pg_trgm` GIN index; matches anywhere. Needs the extension |
| Key length limit | 3,072 bytes | 3,072 bytes (16 KB pages) | btree entry 2,704 bytes |

- The widest key in the 3.0 schema is 2,048 bytes (`taxii_servers`), under both
  limits. The target generator refuses a definition over either limit.
- **`pg_trgm`** is a trusted extension: no superuser is needed if the MISP
  database user may `CREATE` in the database. `runUpgrade` checks for it before
  it takes the instance offline and stops with what to do. See
  [CONFIG.postgresql.md](../CONFIG.postgresql.md).
- A `COMPACT` row format cannot hold a 1,020-byte index key; see §1.

## 4. Ids, sequences and order

- **The next id is kept** across a rebuild. Measured on both MySQL-family
  servers (ten rows, five deleted, next id 11): unchanged after
  `ALTER … ENGINE=InnoDB` and after `ALTER … MODIFY id bigint … ALGORITHM=COPY`.
  PostgreSQL's identity restart is the one that needs care: switching a column
  from `serial` to identity restarts at `MAX(id)`, which would reuse the ids of
  deleted rows. The migration resumes at the greater of `MAX(id)`, the old
  sequence's last value and 1. An incremental push selects `Event.id >
  lastpushedid`, so a reused id would be missed.
- **Children of an event are ordered by id** on every engine in 3.0 (the model's
  `childOrder()`); events keep the implicit primary key order of MariaDB and
  MySQL. Do not rely on a row order the query does not state; PostgreSQL gives
  none.

## 5. What each server refuses

| Statement | MariaDB 10.11 | MySQL 8.4 | PostgreSQL 16 |
|---|---|---|---|
| `ADD COLUMN d datetime NOT NULL` to a table with rows | accepted, rows get `0000-00-00 00:00:00` | **refused** (`1292`, zero date under strict mode) | refused: `contains null values` |
| `ADD COLUMN a TEXT NOT NULL DEFAULT 'x'` | accepted | **refused** (`1101`: a `TEXT` column cannot have a default) | accepted |
| Unparenthesised expression default | accepted | refused | accepted |
| `ALGORITHM=INSTANT` for `int` to `bigint` | refused (`Cannot change column type`) | refused (`Need to rebuild the table`) | not applicable (a rewrite) |
| `ALTER … ROW_FORMAT=DYNAMIC` | cannot be `INSTANT` or `NOCOPY`, even on a `DYNAMIC` table; the same for `ENGINE=InnoDB` | not recorded | not applicable |
| `MODIFY` a `utf8mb3` varchar under a unique key on a `COMPACT` table | error 1709 unless `ROW_FORMAT=DYNAMIC` is in the same statement | not recorded | not applicable |
| A type change over a default that cannot be cast | not applicable | not applicable | fails unless `DROP DEFAULT` is in the same `ALTER` |

The migrations avoid all of these: where a statement would be refused, the
preflight defers the migration with a remedy instead of sending it. Strict mode
also refuses non-ASCII text in an `ascii` column and any truncation, which is why
the preflight checks that the data fits before it narrows a column.

## 6. Upgrading

| | MariaDB | MySQL | PostgreSQL |
|---|---|---|---|
| Plain `utf8mb3` to `utf8mb4` | `INSTANT` (unindexed), `NOCOPY` (indexed) | in place, `COPY` if indexed | not applicable |
| Latin1 / ASCII conversions, `int` to `bigint` | `COPY` | a rebuild (`COPY` or `INPLACE`; never `INSTANT`) | rewrite |
| The `attributes` rebuild | one `COPY` statement; the new indexes' sort files go to `tmpdir` | one `COPY` statement; no sort files in `tmpdir` (measured at 1 M rows) | one rewrite, then 16 `CREATE INDEX` passes; memory and temp space not measured |
| Session settings the migrations set | `alter_algorithm = 'DEFAULT'`, `lock_wait_timeout` of about 300 s | `old_alter_table = OFF`, the same timeout | the same timeout |
| Invalid UTF-8 in a latin1 column | a `?` is substituted | the conversion returns `NULL` | not applicable |
| Atomic DDL | a killed server rolls the `ALTER` back; a rerun converges | a killed client passes; a server kill was not tested | not wrapped in a transaction by MISP |

- **No migration is a transaction on any engine.** The DDL commits implicitly on
  MariaDB and MySQL, and MISP does not wrap it on PostgreSQL. Before anything is
  rendered the declaration is checked against the live schema and what already
  exists is left out, so a run that stopped carries on at the table it failed on.
- **Deferrals** stop a run without failing it. They say what to fix and
  `runUpgrade` is run again. Recorded, on a MariaDB instance coming from 2.5:
  mixed latin1/UTF-8 text in `threat_levels` (fix the rows); two sharing groups
  or two users that are equal under the new collation (rename or change one);
  two blocked events with one uuid (delete one); an organisation index over
  3,072 bytes (drop it).
- **Tag names are case-insensitive** (2.5.47 and later; 3.0 repeats it for its
  collation). Tags that are equal under the collation are merged, the lowest id
  survives. On PostgreSQL the match goes through `lower()`, so `ß` and `ss` stay
  two tags where MySQL merges them.
- **Latin1 columns holding UTF-8 bytes** (the 2.x mojibake) are converted through
  `VARBINARY`, which costs one more rebuild; genuine latin1 is converted
  normally; a column holding both defers.
- **Disk**: about 3.5 times the `attributes` table on MariaDB, half of it in
  `tmpdir`; MySQL writes nothing to `tmpdir` and needs about half of that
  (extrapolated, measured only at 1 M rows); PostgreSQL has not been measured.
  Time and memory: [UPGRADE.md](../UPGRADE.md).
- **Galera**: the `ALTER` runs in total order isolation and blocks the whole
  cluster.
- **The log tables** are left to `Console/cake LogTables upgrade`, which runs
  with the instance online. MariaDB and MySQL swap the tables in one `RENAME
  TABLE`, the new ids starting 10,000 past the old table's last one.
  PostgreSQL swaps inside a transaction that holds the table's lock: the old
  indexes and sequence are renamed with the table, since their names are
  global to the schema. Every engine then copies the old rows back, newest
  first, one id range per statement.

## 7. Raw SQL on PostgreSQL

For code that bypasses the models. MariaDB and MySQL have none of these
problems.

- **Result columns** of a raw query are filed under index `0`, not under the
  table alias: read `$row['Object'] ?? $row[0]`.
- **Unquoted aliases fold to lower case.** `Attribute`, `Object`, `Event` become
  `attribute`, `object`, `event`; the helpers that build conditions (`aclSql()`,
  `likeCondition()`) quote them. Quote your own through `$db->name()`.
- **Booleans** are `TRUE` / `FALSE`: `deleted = 0` fails.
- **MySQL-only syntax**: `FORCE INDEX`, backticks (`` `meta-category` ``) and
  `IF(…)` do not exist.
- **A bare `NULL` is typed text**, so `COALESCE(NULL, 0)` and a `UNION` of `NULL`
  against a number fail without a cast.
- **A duplicate inside a transaction** leaves PostgreSQL's transaction aborted,
  where MariaDB and MySQL lose only the batch (Cake's `insertMulti`).

## How this page was established

- **Measured for this page** (2026-10-19): the string comparisons in §2; the
  default and `NOT NULL` refusals, `INSTANT` and next-id behaviour in §4, §5;
  the row format and strict-mode defaults in §1, on the servers named in §2.
- **Recorded while testing the upgrade** on MariaDB 10.11, MySQL 8.4 and
  PostgreSQL 16 with the copy of a 2.5 instance: the deferrals, the algorithm
  per statement, the time and disk figures, the tag merge, the PostgreSQL SQL
  quirks.
- **Not measured**: PostgreSQL memory and temp space for the index builds, a
  MySQL 8.4 server kill during an `ALTER`, `'ß' = 's'` under the 3.0
  collations, the MySQL disk figure at scale.
