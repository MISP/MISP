# Docker development environment

How to run MISP from a working copy of this repository on top of the
[MISP/misp-docker](https://github.com/MISP/misp-docker) images, so that the
code you edit on your host is the code the container executes.

The short version:

```bash
git clone --recurse-submodules git@github.com:MISP/MISP.git
git clone https://github.com/MISP/misp-docker.git
cd misp-docker && cp template.env .env      # set ADMIN_KEY
# write docker-compose.override.yml (see below), then
docker compose pull && docker compose up -d
```

Paths below assume `~/work/MISP`, `~/work/misp-docker` and `~/work/PyMISP`.

---

## 1. Prerequisites

- Docker Engine 25+ (or Podman 4.9+) and the Compose plugin 2.17+
- Access to `ghcr.io` and Docker Hub for the base images
- Clones of [MISP](https://github.com/MISP/MISP) (with `--recurse-submodules`,
  the submodules carry taxonomies, galaxies, warninglists and misp-objects),
  [misp-docker](https://github.com/MISP/misp-docker) and, if you work on the
  client library, [PyMISP](https://github.com/MISP/PyMISP)

## 2. Configure the stack

In `misp-docker/`:

1. `cp template.env .env`
2. Set `ADMIN_KEY` — the tests and every `curl` example need it, and without
   it the key is autogenerated and you have to dig it out of the logs.
3. Set `BASE_URL` including the port if you do not publish on 443, e.g.
   `BASE_URL=https://localhost:8443` when the override below maps `8443:443`.
   A wrong `BASE_URL` shows up as broken redirects and CSRF failures, not as
   an error message.
4. Optionally set `DEBUG=1` (MISP's `debug` level, `2` adds an SQL dump) so
   errors render in the browser with a stack trace instead of the generic
   "An Internal Error Has Occurred" page. Warnings and exceptions are written
   to `app/tmp/logs/error.log` either way.

## 3. Map your working copy into the container

`misp-core` ships its own copy of the MISP code. A `docker-compose.override.yml`
replaces the directories you work on with bind mounts from your clone:

```yaml
services:
  misp-core:
    ports:
      - "8080:80"
      - "8443:443"
    extra_hosts:
      - "host.docker.internal:host-gateway"
    volumes:
      - "~/work/MISP/app/composer.json:/var/www/MISP/app/composer.json"
      - "~/work/MISP/app/phinx.php:/var/www/MISP/app/phinx.php"
      - "~/work/MISP/app/Console:/var/www/MISP/app/Console"
      - "~/work/MISP/app/Controller:/var/www/MISP/app/Controller"
      - "~/work/MISP/app/Db:/var/www/MISP/app/Db"
      - "~/work/MISP/app/Error:/var/www/MISP/app/Error"
      - "~/work/MISP/app/Locale:/var/www/MISP/app/Locale"
      - "~/work/MISP/app/Model:/var/www/MISP/app/Model"
      - "~/work/MISP/app/Plugin:/var/www/MISP/app/Plugin"
      - "~/work/MISP/app/View:/var/www/MISP/app/View"
      - "~/work/MISP/app/Lib/Dashboard:/var/www/MISP/app/Lib/Dashboard"
      - "~/work/MISP/app/Lib/EventReport:/var/www/MISP/app/Lib/EventReport"
      - "~/work/MISP/app/Lib/Export:/var/www/MISP/app/Lib/Export"
      - "~/work/MISP/app/Lib/Migration:/var/www/MISP/app/Lib/Migration"
      - "~/work/MISP/app/Lib/Tools:/var/www/MISP/app/Lib/Tools"
      - "~/work/MISP/app/Lib/WorkflowModules:/var/www/MISP/app/Lib/WorkflowModules"
      - "~/work/MISP/app/webroot/js:/var/www/MISP/app/webroot/js"
      - "~/work/PyMISP:/var/www/MISP/app/PyMISP"
      - "./core/files/enable_xdebug.sh:/custom/files/customize_misp.sh"
```

Notes, in decreasing order of how much time they save:

- **Mount `app/Lib/` per subdirectory, never the whole thing.** `app/Lib/`
  contains the vendored CakePHP (`app/Lib/cakephp`, a submodule) and mounting
  the parent shadows it. The flip side is that the list has to be kept in
  sync: a new top-level directory that exists in your branch but not in the
  image is simply absent at runtime. That failure is a hard fatal with no
  hint about mounts, e.g. `Trait "LegacyMigrationsTrait" not found` when
  `app/Lib/Migration/` is missing from the list.
- Do **not** mount `app/Config/` or `app/tmp/`: the compose file already
  mounts `./configs/` and `./logs/` there, and the entrypoint generates the
  config from `.env` on every start.
- Mount only `app/webroot/js` rather than all of `app/webroot`, so the
  container keeps its own `webroot/img/orgs`, attachments and other
  runtime-written content.
- Compose does not expand `~`; use absolute paths in the real file.
- The service is `misp-core`. Older guides say `misp`, which silently creates
  a second, unused service.
- `files/taxonomies`, `files/misp-objects` and friends can be mounted from
  your clone too, but only if you want to develop against your own submodule
  checkouts — the image ships working copies.

Then start the stack:

```bash
cd ~/work/misp-docker
docker compose pull          # or: docker compose build
docker compose up -d
docker compose ps
```

MISP is then on `https://localhost:8443` (per `BASE_URL` above).

`misp-core` staying `(unhealthy)` while the site works is expected with a
port-mapped `BASE_URL`: the healthcheck curls `${BASE_URL}/users/heartbeat`
from *inside* the container, where nginx listens on 443, not on 8443. Check
the real thing instead:

```bash
docker compose exec misp-core curl -ks -o /dev/null -w '%{http_code}\n' \
    https://localhost/users/heartbeat
```

### Permissions

The container runs as `www-data` (uid/gid 33). Anything it writes on a bind
mount is owned by 33 and mode 0770, so `misp-docker/logs/` is not readable by
your host user. Read the logs from inside the container instead:

```bash
docker compose exec misp-core tail -f /var/www/MISP/app/tmp/logs/error.log
```

If you would rather read them from the host, add yourself to gid 33 or set an
ACL on the directory; `chmod -R 777` on the repository is not the answer,
since the code you mount also has to stay writable only by you.

## 4. Custom MISP modules

`misp-modules` loads extra modules from `/custom/` at startup, which the
compose file maps to `misp-docker/custom/<kind>/`:

```
custom/action_mod/  custom/expansion/  custom/export_mod/  custom/import_mod/
```

Drop a module in the matching directory and restart the service — the modules
are read once at boot:

```bash
docker compose restart misp-modules
docker compose exec misp-core curl -s http://misp-modules:6666/modules
```

Then enable it in MISP (`Administration > Server Settings > Plugin settings`,
or from the CLI):

```bash
CAKE="/var/www/MISP/app/Console/cake"
docker compose exec -u www-data misp-core \
    $CAKE Admin setSetting Plugin.Enrichment_services_enable 1
docker compose exec -u www-data misp-core \
    $CAKE Admin setSetting Plugin.Enrichment_services_url http://misp-modules
docker compose exec -u www-data misp-core \
    $CAKE Admin setSetting Plugin.Enrichment_<module_name>_enabled 1
```

A module that does not show up in the UI is almost always either not enabled,
or not applicable to the attribute/object you are expanding: the module choice
list is filtered on `mispattributes['input']`, which for an object module has
to contain the **object name** (`domain-ip`), not an attribute type.

There is no cache to clear — `Module::getModules()` asks the server on every
page load — but it gives up after **one second**, and a timeout is reported as
"Module service not reachable", the same as a module server that is down. If
the list is empty right after a restart, or while you are sitting on a
breakpoint in a host-run server, that one-second budget is the reason.

## 5. Developing misp-modules

Section 4 covers dropping a single module into `custom/`. To work on the
[misp-modules](https://github.com/MISP/misp-modules) codebase itself, mount
your clone over the copy installed in the container. The install path is
version-specific, so ask the container where the package is:

```bash
docker compose exec misp-modules \
    python -c "import misp_modules, os; print(os.path.dirname(misp_modules.__file__))"
# /usr/local/lib/python3.14/site-packages/misp_modules
```

Add that to `docker-compose.override.yml`:

```yaml
services:
  misp-modules:
    volumes:
      - "~/work/misp-modules/misp_modules:/usr/local/lib/python3.14/site-packages/misp_modules:ro"
```

The `/custom/` mounts keep working alongside it. What you get is the code
from your clone with the image's dependency set — which is the catch: a
module whose new dependency is not in the image fails to import, and you
either add it for the session (`docker compose exec -u root misp-modules pip
install <dep>`, lost the next time the container is recreated) or rebuild the
image. The build args clone from GitHub, so `MODULES_COMMIT` only helps once
your work is pushed somewhere the Dockerfile can fetch it.

### The edit/reload loop

Modules are imported once, when the server boots. After every edit:

```bash
docker compose restart misp-modules
docker compose logs -f misp-modules
```

The boot log is where you find out why a module is missing from the list: a
module that loads is logged at INFO, one that does not is logged at WARNING
with its `ImportError` message, both visible by default.

```
misp-modules | INFO - Parsing custom modules from root directory: /custom/
misp-modules | INFO - CUSTOM MISP module test_domain_ip_expansion (type=expansion) imported
misp-modules | WARNING - CUSTOM MISP module broken_module (type=expansion) failed: No module named 'foo'
misp-modules | INFO - MISP modules server started on 0.0.0.0:6666
```

Add `-d` for debug-level logging of the requests themselves, by overriding
the entrypoint (the image's is `misp-modules -l 0.0.0.0 -c /custom/`):

```yaml
services:
  misp-modules:
    entrypoint: ["/usr/local/bin/misp-modules", "-l", "0.0.0.0", "-c", "/custom/", "-d"]
```

### Querying a module without MISP

The server speaks plain HTTP on 6666. `GET /modules` returns the
introspection of everything that loaded, and `POST /query` runs one module on
a payload you control — no event, no UI, no cache in between:

```bash
docker compose exec misp-core curl -s -X POST http://misp-modules:6666/query \
    -H "Content-Type: application/json" -d '{
      "module": "test_domain_ip_expansion",
      "object": {
        "name": "domain-ip",
        "Attribute": [
          {"object_relation": "domain", "value": "example.com", "type": "domain"},
          {"object_relation": "ip", "value": "198.51.100.42", "type": "ip-dst"}
        ]
      }
    }'
```

Attribute modules receive `{"module": ..., "attribute": {...}, "event_id": ...}`
and object modules `{"module": ..., "object": {...}, "event_id": ...}`; both are
assembled in `EventsController::__queryEnrichment()` and
`__queryObjectEnrichment()` and sent by `Module::queryModuleServer()`. A
module in `misp_standard`
format answers with `{"results": {"Object": [...], "Attribute": [...]}}`, and
any module can answer `{"error": "..."}`, which MISP surfaces as a flash
message.

Reproducing a payload exactly as MISP sends it is worth the detour when a
module behaves differently in the UI than on the command line — that
difference is usually the event/object context, not the module.

### Running the server from the host instead

If you would rather run misp-modules outside Docker — native debugger, no
restarts — install it from your clone and point MISP at the host gateway:

```bash
cd ~/work/misp-modules
poetry install
poetry run misp-modules -l 0.0.0.0 -d
```

Bind to `0.0.0.0`, not to `127.0.0.1`: the request arrives from the container
over the docker bridge (`host.docker.internal` resolves to the gateway,
`172.17.0.1` here), so a loopback-only server is unreachable. If binding on
every interface bothers you, bind that bridge address instead.

```bash
CAKE="/var/www/MISP/app/Console/cake"
docker compose exec -u www-data misp-core \
    $CAKE Admin setSetting Plugin.Enrichment_services_url http://host.docker.internal
docker compose exec -u www-data misp-core \
    $CAKE Admin setSetting Plugin.Enrichment_services_port 6666
```

`host.docker.internal` resolves inside `misp-core` thanks to the
`extra_hosts: host.docker.internal:host-gateway` entry in the override, and
the same two settings exist per module family (`Import_services_url`,
`Export_services_url`, `Action_services_url`). Remember to point them back at
`http://misp-modules` when you are done, or the stack only works while your
host process is running. The trade-off is the dependency install: the full
`poetry install` pulls the whole module ecosystem, which is slow and needs
build tooling that the image already has.

### Tests and docs in the misp-modules repo

The suite is an integration suite: it POSTs to a **running** server on
`http://127.0.0.1:6666/`, so start one first — `poetry run misp-modules` on
the host (loopback is fine here, the tests run on the host too), or publish
6666 from the container.

```bash
cd ~/work/misp-modules
poetry install --with test          # pytest lives in the 'test' group
poetry run pytest tests/test_expansions.py -k <module_name>
```

Many expansion tests hit live third-party services and read keys from
`tests/expansion_configs.json`, so run the subset for the module you touched
rather than the whole file. The module contract itself — `handler()`,
`introspection()`, `version()`, `mispattributes`, config values, object vs
attribute input — is documented in that repo under
`documentation/mkdocs/contribute.md`; the per-module pages are generated from
each module's `moduleinfo` by `documentation/generate.py`, so keep that dict
accurate.

## 6. XDebug

The image has no XDebug. `core/files/enable_xdebug.sh` in misp-docker installs
and configures it, and the `customize_misp.sh` mount above runs it on every
container start. The entrypoint executes `/custom/files/customize_misp.sh` if
it is executable, so:

```bash
chmod +x core/files/enable_xdebug.sh
```

Two things to check in that script:

- The `conf.d` path is PHP-version specific (`/etc/php/8.4/...` for current
  2.5 images). Derive it instead of hardcoding if you switch image tags:
  `PHP_VER=$(php -r 'echo PHP_MAJOR_VERSION.".".PHP_MINOR_VERSION;')`.
- The setting is `xdebug.start_with_request`, not
  `xdebug.xdebug.start_with_request`. The doubled prefix is ignored, and
  breakpoints then never hit.

VS Code, listening on 9999 (`host.docker.internal` from inside the container):

```json
{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "Listen for Xdebug",
            "type": "php",
            "request": "launch",
            "port": 9999,
            "pathMappings": {
                "/var/www/MISP/app": "${workspaceRoot}/app"
            }
        }
    ]
}
```

For CLI (`cake`) debugging, inside the container:

```bash
export XDEBUG_MODE=debug XDEBUG_SESSION=1
```

## 7. Everyday commands

All of these run in `misp-docker/`. `cake` must run as `www-data`, or it
writes root-owned cache files that break the web user afterwards.

```bash
# shell as the web user
docker compose exec -u www-data misp-core bash

# enable/disable the instance
docker compose exec -u www-data misp-core \
    /var/www/MISP/app/Console/cake Admin live 1

# apply DB updates after pulling / switching branch
docker compose exec -u www-data misp-core \
    /var/www/MISP/app/Console/cake Admin runUpdates
docker compose exec -u www-data misp-core \
    /var/www/MISP/app/Console/cake Admin migrationStatus

# container logs
docker compose logs -f misp-core
```

`cake Live 1` still works but is deprecated in favour of `cake Admin live`.

`docker compose exec` lands you as root, hence the explicit `-u www-data`.

After a `git pull` on the host, refresh the submodules too — they carry the
taxonomies, galaxies, warninglists and object templates, and they are what
you mount if you added `app/files/...` to the override:

```bash
cd ~/work/MISP && git submodule update --init --recursive
```

Schema changes are migrations under `app/Lib/Migration/Migrations/`; see
[database-migrations.md](database-migrations.md) before touching the schema.

## 8. Running the tests

The live tests in `tests/` talk to the instance over **plain HTTP** (they build
`http://$HOST`), so point `HOST` at the HTTP port, not the HTTPS one:

```bash
cd ~/work/MISP
export HOST=localhost:8080
export AUTH=<the ADMIN_KEY from misp-docker/.env>
python3 tests/testlive_comprehensive_local.py -v
python3 tests/testlive_security.py -v
python3 tests/testlive_sync.py -v
```

`tests/curl_tests_GH.sh $AUTH $HOST` is the CI smoke test. It uses relative
paths (`event.json`, `../app/Console/cake`), so it has to run from `tests/`
on a host that also has the MISP CLI — in this setup that means inside the
container, with the repository mounted there.

PyMISP's own suite runs from the PyMISP clone, with poetry, against the same
instance. Create `tests/keys.py` there:

```python
url = "https://localhost:8443"
key = "<the ADMIN_KEY from misp-docker/.env>"
```

(`tests/keys.py` only has to define `url` and `key`; the suite disables
certificate verification by itself, which is what you want against the
self-signed certificate the container generates.)

```bash
cd ~/work/PyMISP
poetry install -E fileobjects -E openioc -E virustotal -E docs -E pdfexport -E email
poetry run pytest tests/test_mispevent.py           # offline
poetry run pytest tests/testlive_comprehensive.py   # needs the instance
```

PHP lint and unit tests run inside the container, where the vendor directory
lives:

```bash
docker compose exec misp-core bash -c \
    "cd /var/www/MISP && app/Vendor/bin/parallel-lint \
     --exclude app/Lib/cakephp/ --exclude app/Vendor/ -e php,ctp app/"
docker compose exec misp-core bash -c \
    "cd /var/www/MISP && app/Vendor/bin/phpunit app/Test/"
```

## 9. Contributing the change back

Read [CONTRIBUTING.md](../../CONTRIBUTING.md) and
[CODINGSTYLE.md](../../CODINGSTYLE.md) first. In short:

1. Fork MISP on GitHub and add your fork as a remote:
   `git remote add myuser git@github.com:myuser/MISP.git`
2. Branch off the branch your change targets, and say which one in the PR.
   `develop` is where ordinary work lands and is merged into the stable `2.5`
   at release time; `2.5` itself only takes urgent hotfixes outside that
   cycle: `git checkout develop && git checkout -b fix-annoying-bug`
3. Commit only the files you changed. `git status` in this repo is noisy
   because the submodules under `app/files/` move on their own; never commit
   a submodule bump you did not intend.
4. Use the gitchangelog prefixes, they drive the changelog:
   `fix: [api] Correct attribute validation (#3120)`, `new: [...]`,
   `chg: [...]`.
5. `git push myuser fix-annoying-bug`, then open the pull request,
   describing what it fixes and how to reproduce it.
